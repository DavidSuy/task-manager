# Week 5 Retrospective — Plan Mode and Subagent Decomposition

**1 — Plan Mode value.** The clearest case was Session 1 in `PLAN_LOG.md`. The original plan for `create_task` used `isinstance(priority, int)` and explicitly noted that `True` would pass as priority 1, then kept it "to mirror the file's existing style". I amended the plan to reject bools first and add `test_create_task_invalid_priority_bool`. Without that amendment, Session 2's route change (`POST /api/tasks`) would have accepted the JSON body `{"priority": true}` and silently created a priority-1 (*urgent*) task, and the service tests from Session 1 would have locked that behavior in. Fixing it later would have meant reverting committed code and tests across two sessions. Session 2 shows the same pattern at smaller scale: the plan read `data["title"]`, which turns a missing title into a raw `KeyError` and a 500, and hardcoded `data.get("priority", 3)`, which duplicated the service default in `routes/api.py`. Both were caught at plan time, not in a diff.

**2 — Plan Mode limits.** In Session 3 the amended plan said to add `update_task_priority` "to the existing import line" in `tests/test_tasks.py`. Claude instead rewrote that line into a five-line parenthesized import. In Session 4 the plan said `list_tasks` would go "after `_validate_priority` is defined, since it calls it", and Claude put it before. Both changes are harmless (ruff still reports the same 6 errors; Python looks up names at call time), but neither is what I approved. I caught them only by reading `git diff`, not from Claude's summary, which said the work matched the plan. The bigger limit appeared before Session 2 (see Notes in `PLAN_LOG.md`): after `/clear` the session was not actually in Plan Mode, Claude printed a plan, got "You are not in plan mode", and went on to edit `routes/api.py` and `tests/test_tasks.py` with no approval. My conclusion: Plan Mode is reliable for *what* gets built (every amendment in Sessions 1–4 was implemented) but not for *exactly how* the edit is made, and it is not enforced at all — the approval step is something Claude respects, not something the tool guarantees.

**3 — Subagent value.** The most important boundary was SA-3's: `routes/api.py` only, with `services/users.py` read-only and "no validation in the route". Task 1 shows why. When a single session owned both layers, Claude kept leaking service concerns into routes: the hardcoded default in Session 2, and in Session 4 a route error message that copied the service's "must be an integer between 1 and 5" wording. With the boundary fixed in `DECOMPOSITION.md`, SA-3 produced three routes that only call `list_users`, `get_notification_pref` and `update_notification_pref`, and all validation stayed in `services/users.py`. The SA-4 boundary (tests only, no edits to `services/` or `routes/`) mattered for a different reason: SA-4 wrote tests against the contract in SA-3's Hand-off field, not against code it had just written, and they passed on the first run (55 passed). In a single session, I expect validation would have ended up split across `routes/api.py` and `services/users.py`, and the tests would have been fitted to whatever the implementation did, including the 500 on non-object JSON bodies that I found by manual testing after SA-3.

**4 — Gap analysis.** Both techniques depend on Claude choosing to comply: Plan Mode was skipped entirely once, and every subagent's Constraint field was followed only because Claude respected the prompt. The rule from Task 2 I would most want enforced mechanically is the Output field — each subagent may edit only the files listed for it (e.g. SA-3 may edit only `routes/api.py`). A `PreToolUse` hook on `Edit`/`Write` would read the current subagent's allowed paths from a file such as `.claude/allowed_paths` and block, with an error message naming the allowed files, any edit whose target path is not on that list.
