# Justification

**Commands.** I wrote every command exactly as it runs in this repo, including `source .venv/bin/activate`, because the WSL system Python has no pytest and an unactivated session fails before doing any work. Session 1 shaped this section most: Claude ran `pytest -v` but skipped `ruff check .`, because only the test line said "run before finishing every task." After I gave the lint line the same trigger and the 6-error baseline, Claude ran ruff in Sessions 2 and 3 and reported "exactly the pre-existing 6 errors." If I had to cut, I would drop the one-time setup line and keep the activate rule.

**Architecture.** I described the layers that actually exist, `routes/api.py` → `services/*.py` → the module-level `TASKS`/`USERS` dicts, and did not claim a repositories layer, because pointing Claude at a layer that isn't there invites it to invent one. The canonical-example line naming `services/users.py` did the most work: in Session 1 Claude read users.py before editing and said it was matching get_user's pattern. No session tried to add a route, so the "no business logic in routes" rule was never tested. I would cut the Blueprint and `handle_app_error` details first, since Claude can read them from `routes/api.py` directly.

**Conventions.** Each rule names the exact class or function to copy (`NotFoundError("Task")`, `get_user`, `create_user`), because "handle errors properly" gives Claude nothing to imitate. Session 2 shaped it most: Claude copied create_user's title check but let `create_task("x", 999)` return 201 for a nonexistent user, because the example it was told to follow never checks another service. After I added the `get_user(user_id)` rule, Session 3 called it and cited "the project rule." To halve this section I would keep the error, user_id and test-assertion rules and drop the type-hint line, which Claude followed from the users.py example alone.

**Do not touch.** These rules protect things Claude could "fix" while keeping tests green: the 404/422 codes in `utils/errors.py`, signatures that `routes/api.py` depends on, and the existing tests, which an agent could weaken to make a broken change pass. No session violated them. Session 3 extended the test file's import line but left all four original tests intact. I would keep the tests and errors.py rules and drop `DRILL_PROMPTS.md`, which no session touched.

**Team use.** With three developers, my first change would be separating shared rules from personal setup: the committed CLAUDE.md keeps project rules, while machine-specific details like the venv activation move to each developer's uncommitted CLAUDE.local.md. My second change would be treating CLAUDE.md like code, so every rule change goes through PR review with the session evidence behind it ("I added X because Claude did Y"), which keeps three people from adding contradictory rules. The hard-coded "6 errors" ruff baseline would also go stale within days of three people committing, so in a team I would replace it with a CI lint check rather than a number in the file.
